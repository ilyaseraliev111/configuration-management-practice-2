# Устройство программы и связь с лекциями

## Командная строка

Программа получает опции через argv. argparse проверяет обязательные аргументы
и тип глубины; настройки доступны как Config. Результат идёт в stdout,
диагностика — в stderr. Код 0 — успех, 1 — ошибка данных/сети, 2 — ошибка CLI.
Программа завершается после одного анализа, не ожидая команд как оболочка из ПР1.

## Менеджеры пакетов

Пакет имеет имя, версию и метаданные. Репозиторий содержит сведения о пакетах.
Вместо установки пакета анализатор получает APKINDEX.tar.gz.
P и V выбирают запись, D содержит прямые ограничения, p — предоставляемые возможности.
Например, busybox зависит от so:libc.musl-x86_64.so.1.
musl предоставляет это имя, поэтому в графе появляется ребро busybox -> musl.
Версия ABI предоставляемого имени и версия самого musl — разные значения.

У APK собственные правила версий: 1.10 новее 1.9, 1.0_rc1 старее 1.0,
ревизия -r10 новее -r2 при одинаковой основной версии.
Простая сортировка строк и правила SemVer не заменяют правила APK.
Разные ограничения могут дать в графе две версии одного имени.
Это данные анализа; глобальный план установки не относится к текущим трём этапам.

## Конфигурационные языки

Настройки задаются через CLI, как требует вариант 29.
JSON используется для данных тестового графа: пакетов и зависимостей.
Циклы задаются ссылками на имена, без рекурсивного вложения объектов.
Повторы ключей и нарушения схемы выявляются. При чтении не исполняется Python-код;
eval и сторонние JSON/конфигурационные библиотеки не используются.

## Граф и BFS

Вершина — конкретный пакет имя=версия. Ребро A -> B означает, что A зависит от B.
Корень помещается в очередь. Извлекается первый пакет, его зависимости разрешаются
в записи репозитория. Новые узлы добавляются в конец очереди.
Сначала открывается глубина 1, затем 2 и так далее.

Словарь depths хранит минимальную глубину и признак посещения.
В цикле A -> B -> C -> A корень не ставится в очередь повторно,
но последнее ребро C -> A сохраняется. В ромбе A -> B/C -> D
вершина D одна, а входящих рёбер два.
Глубина 0 не раскрывает корень; глубина 1 показывает его прямые зависимости.
Итеративный обход не расходует стек Python на рекурсивные вызовы.

## Git

Первый коммит — CLI, второй — HTTP и APKINDEX, третий — BFS и JSON.
Ветки сохраняют соответствующие снимки. main сейчас указывает на третий этап.
Ветки могут содержать разные файлы, потому что это разные состояния разработки.
Новые этапы добавляются коммитами без переписывания готовой истории.
Для продолжения можно создать stage4-operations от main, когда этап будет изучен.
